> ### Slot model (recommended: the simplest design that works)
> - **Represent everything as local wall time. Never do date arithmetic on instants.** A slot id is `"YYYY-MM-DDTHH:MM"` in Europe/Bratislava, with no offset. Calendar dates are moved with `Date.UTC(y, m-1, d+i)` and `getUTCDay()`. A day therefore never has 23 or 25 hours, and the server's time zone has no effect.
> - **The only time zone conversion** is `localNow(now): { date, minutes }`. It uses `Intl.DateTimeFormat("en-CA", { timeZone: TIME_ZONE, hourCycle: "h23", ... }).formatToParts(now)`. Use `hourCycle: "h23"` to avoid getting hour "24" at midnight.
> - **Generation:** `generateSlots(now)` loops over `i = 0..HORIZON_DAYS-1`:
> - `date = addDays(today, i)`
> - skip the date if `OPENING_HOURS[dow]` is null or the date is in `CLOSED_DATES`
> - slot starts run from `open` while `start + SLOT_MINUTES <= close`, so the last slot is 17:30 Tue–Sat and 11:30 on Sunday
> - keep a slot only if `i*1440 + start >= nowMinutes + LEAD_MINUTES`
> - **Defaults** (constants in `slots.ts`):
>
> | Constant | Value |
> |---|---|
> | `SLOT_MINUTES` | 30 |
> | `LEAD_MINUTES` | 120 |
> | `HORIZON_DAYS` | 14 |
> | `SLOT_CAPACITY` | 4 orders |
> | `CAKE_NOTICE_DAYS` | 2 (the order's slot date must be at least `today + 2`, following the comment at `menu.ts:7`) |
> | `MAX_QTY` | 20 per item |
>
> - **DST:** opening hours (07:00–18:00) never touch the 02:00–03:00 changeover, so every slot is a real local time that occurs only once. Lead time is compared in wall-clock minutes, which can be off by one hour only on a changeover night. The gap from before 02:00 to the first 07:00 slot is always at least 4 hours, so this is exact for any `LEAD_MINUTES ≤ 240`. Write that limit as a comment on the constant.
> - **Capacity and storage (no DB): in-memory storage behind an interface.** This is the recommendation. The shop email is the lasting record. A JSON-file store can replace it later without other changes.
> ```ts
> interface OrderStore {
>   /** Atomic: insert only if fewer than `capacity` orders hold order.slot. false = full. */
>   reserve(order: Order, capacity: number): Promise<boolean>;
>   cancel(id: string): Promise<void>;
>   get(id: string): Promise<Order | undefined>;
>   countBySlot(): Promise<Map<string, number>>;
> }
> ```
> `InMemoryOrderStore` must do the count and the insert synchronously, with no `await` in between. That keeps it atomic in single-threaded Node. The `Order` type has: `id` (8 random hex characters from `crypto.randomBytes(4)`), `slot`, `lines` with `{productId, qty, unitPriceCents}`, `totalCents`, `name`, `email`, `phone?`, `note?`, `lang` and `createdAt`.
> - **Request flow for `POST /order`:**
> 1. Read `now()` once and parse with zod. Field names are flat `qty_<productId>` because `urlencoded` runs with `extended: false`.
> 2. Check that the slot is in `generateSlots(now)`.
> 3. Apply the cake rule.
> 4. Price the lines from `MENU`.
> 5. `reserve`, then send the shop mail. If that send fails, call `cancel(id)` and `next(err)`.
> 6. Send the customer mail. If it fails, log it and still count the order as placed.
> 7. Redirect 303 to `/?lang=xx&order=<id>#order`.
>
> All errors re-render with status 400, one error code (`invalid | empty | slotTaken | cakeNotice`) and the escaped values. The form action is `/order?lang=xx#order` so the 400 page scrolls to the form.

> ### Risks
> - **Data loss:** in-memory orders and slot counts disappear on restart, which can lead to overbooking afterwards. Running more than one process splits capacity. The shop email is the lasting record. If restarts happen often, a JSON-file store is the next step.
> - **Abuse:** with no payment and no login, fake orders can fill every slot, and the customer confirmation email can be used to send mail to third parties. Quantity caps limit this. A honeypot field and rate limiting would be cheap follow-ups.
> - **Email header injection:** the existing contact form already puts `name` into the subject (`app.ts:36`). Order subjects must not contain user input, and `name`/`phone` must reject CR/LF. Flag `app.ts:36` to the reviewer as a separate issue.
> - **Time zone bugs:** any use of `getDay`, `getHours`, `toLocaleDateString` without `timeZone`, or `+86400000` breaks near midnight and at DST changes. The `TZ` override in the tests catches this.
> - **Overbooking race:** if a future store implementation puts an `await` between counting and inserting, two orders can take the last place in a slot.
> - **Express 4 does not catch async rejections:** `GET /` and `POST /order` need try/catch with `next(err)`.
> - **Untrusted prices:** prices must come from `MENU` in integer cents. Format them only when rendering.

> The time logic holds up. The weak part is per-slot capacity built on an in-memory store. Line references are relative to `~/code/kvasok-site/`.

> **Objections**
>
> - 🟠 **Should change: capacity is enforced from a store that is wiped on every restart.**
> - **Evidence:** CLAUDE.md:3 says "no database yet". `npm run dev` is `tsx watch` (package.json:6), which restarts the process on every edit. index.ts:5 builds one app per process. The plan accepts "in-memory storage is acceptable for v1 (shop email is the record)".
> - **Effect:** after any deploy or crash, `countBySlot` starts at 0 again, so a slot that already has 4 orders can take 4 more. Every `/?order=<id>` link from before the restart stops showing the confirmation.
> - **Fix:** the shop email being the record doesn't make the "4 per slot" promise true. Either persist orders to a JSONL file (load at boot, `appendFileSync` in `reserve`, about 25 lines, no new dependency), or drop capacity for v1 (see Cheaper alternative). The plan should also say what `/?order=<unknown id>` renders.
> - 🟠 **Should change: anyone can fill every slot, and the shop can't free one.**
> - **Evidence:** the plan sets "4 orders per 30-min slot" and "no online cancellation". The app has no rate limiting (app.ts:17-20). `OrderStore.cancel` is only called when the shop mail fails.
> - **Effect:** 14 days × about 22 slots × 4 is roughly 1,000 POSTs, and then nobody can order online until a restart. A restart also deletes the real orders. Each fake order also sends a "customer" mail to whatever address was typed in. With pay at pickup and cakes "made to order" (menu.ts:7), fake cake orders cost real ingredients.
> - **Fix:** if capacity stays, the shop needs a way to release a slot. That could be a token-protected cancel link in the shop mail, plus a limit on open orders per email address. Keep free text (the note) out of the customer mail.
> - 🟠 **Should change: an async `GET /` on Express 4 can crash the server.**
> - **Evidence:** the plan says "GET / is async". The project uses express 4.21.2 (package.json:12). Express only forwards rejected promises to `next` from version 5 on (https://expressjs.com/en/guide/error-handling.html). On Node ≥15, an unhandled rejection kills the process, which here also wipes the in-memory store.
> - **Fix:** keep the `OrderStore` methods synchronous, since the only implementation is synchronous, and leave `GET /` synchronous. Otherwise wrap it in try/catch → `next(err)`, the same way app.ts:34-40 does.
> - 🟡 **Consider: the ID's case won't match the regex.** `crypto.randomBytes(4).toString("hex")` gives lowercase letters, but the confirmation check is `^[0-9A-F]{8}$`. As planned, the confirmation would never show. Call `.toUpperCase()` when creating the ID, or make the regex case-insensitive.
> - 🟡 **Consider: `now?` has to be a clock function, not a Date.** index.ts:5 creates the app once. If `now` is a Date captured at `createApp` time, the live server would show slots frozen at boot time. Type it as `() => Date` and call it once per request. A related case: a slot that was valid at GET but passed the 120-minute lead time before POST (likely for the earliest slot) currently returns the generic `invalid` code. Give it its own "slot no longer available" message and re-render with fresh slots.
> - 🟡 **Consider: the cake rule is undefined and the quantity cap is too high for cakes.** "2 days' notice" could mean calendar dates or 48 hours. It also doesn't say whether closed Monday (hours.ts:4) counts as a baking day. Store the rule as a constant, not just a comment in menu.ts. `MAX_QTY` 20 lets one unverified form order 20 × medovník at €38 each (menu.ts:18), which is €760 to bake on spec. Set a lower limit for cakes.
>
> **Cheaper alternative:** For v1, drop the per-slot capacity. Slots become validated pickup times: opening hours, lead time, horizon, `CLOSED_DATES` and the cake notice. That removes `OrderStore`, `reserve`/`cancel`/`countBySlot`, the parallel test, disabled options and the `slotTaken` error, and `GET /` stays synchronous. POST becomes validate → price → shop mail → customer mail → `303 /?lang=xx&ordered=<ID>#order`, which follows the existing `sent=1` pattern (app.ts:37). The confirmation shows a generic "order <ID> received, check your email" message. The shop email is the record, as the plan already says, and the shop phones the customer if a slot is overloaded. Add capacity once there is real persistence. This still meets "add online ordering with pickup time slots", removes roughly a third of the plan, and removes the first three objections.
